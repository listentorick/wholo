# ADR-076 — Delivery Tokens: Public-Key Signatures, Checked First at the Edge

**Status**: Accepted
**Date**: 2026-10-11
**Deciders**: Rick Walsh
**Related**: ADR-059 (delivery link token design — amended by this ADR), ADR-049 (JWT validation against JWKS), ADR-026 (BFF per portal)

---

## Context

ADR-059 made the QR link on a printed manifest a signed pointer to an order: `<orderId>.<signature>`, sent as the `X-Delivery-Token` header, with the signature an HMAC over the order id. The routes that accept it have no login; the token is the only credential.

A review of the `multer` advisories found three weaknesses in how that token was handled:

1. **It was checked too late.** In both the driver BFF and `apps/api`, the photo upload's `FileInterceptor` (multer) parsed the request body before any code looked at the token. The BFF did not check it at all; it forwarded everything. Anyone on the internet could reach the body parser of a public service.
2. **Checking it needed the minting secret.** An HMAC is verified by recomputing it, so whatever can verify a token can also create one. The BFF could only have checked tokens by holding the key that forges them. No BFF holds a signing key or any other secret, and the public-facing pod is the last place to put one.
3. **The key failed open.** The chart defaulted `api.deliveryTokenSigningKey` to an empty string and always rendered it; `DeliveryTokenSigner` only rejected a missing variable. An environment that never set the key signed links with an empty HMAC key, which anyone could reproduce.

No delivery links were in real use when this was decided, so the token format could change without a migration period.

## Decision

### 1. Ed25519 signatures instead of an HMAC

The token keeps its shape, `<orderId>.<base64url(signature)>`, but the signature is Ed25519 over the order id.

- **The private key** is held only by `apps/api` (and the worker, the same image). It is the only thing that can create a link. `DELIVERY_TOKEN_PRIVATE_KEY`, in the `wholo-api` Secret.
- **The public keys** are given to `apps/api`, the worker and the driver BFF as ordinary config, `DELIVERY_TOKEN_PUBLIC_KEYS`. A public key can check a link and cannot create one.

This is the same model as login tokens (ADR-049): the issuer signs with a private key; everything else verifies with public keys.

Ed25519 signatures are deterministic, so ADR-059's property holds unchanged: the same order always produces the same URL, and a reprinted manifest reproduces an identical QR code. The signature is 86 characters instead of 43, which makes the QR code slightly denser. Ed25519 is in Node's `crypto`; no dependency is added.

Keys are stored as base64 of their DER encoding (PKCS#8 private, SPKI public), one line each, generated by `scripts/generate-delivery-token-keys.sh`.

### 2. The public keys are a list

A token is valid if **any** listed key verifies it. ADR-059's reason for links never expiring — a driver in the field cannot get a replacement QR code — applies equally to replacing the key, which under the HMAC design killed every outstanding link at once. With a list, a planned replacement trusts the new key, then signs with it, and only drops the old key once the manifests printed with it are delivered. Dropping the old key immediately remains the response to a compromise. The procedures are in `docs/runbook/keys-and-certificates.md`.

### 3. The token is checked first, in both services

- **Driver BFF** — `DeliveryTokenGuard` on the whole `DeliveryLinksController` verifies the signature (`DeliveryTokenVerifier`) and answers 404 otherwise. Nothing is forwarded to `apps/api` for an unverified request.
- **`apps/api`** — `DeliveryLinkGuard` on `DeliveryLinksController` verifies the signature, loads the order, rejects a cancelled or rejected one, and hands the order to the handler through `@DeliveryOrder()`. The service's methods take that resolved order, not a raw token, so they cannot run for an unverified caller.

Both are NestJS guards because guards run before interceptors: a request without a genuine token is refused before multer reads its body. An integration test proves the ordering — an oversized upload gets 413 with a genuine token and 404 without one.

The BFF checks the signature only. It has no database; whether the order can still be delivered remains `apps/api`'s check. The responses are as in ADR-059: 404 for any token that does not verify, 410 for an order that can no longer be delivered, never saying which check failed.

The verify logic is duplicated in the BFF (about 30 lines) rather than shared, so that no signing code is ever built into the public-facing image.

### 4. Fail closed

- Both services refuse to start if a key is missing, empty, unparseable or not Ed25519, and `apps/api` also refuses if its private key's public half is not in the list (it would otherwise print links nothing accepts). Error messages never include the private key.
- The chart refuses to render without `deliveryToken.privateKey` and at least one `deliveryToken.publicKeys` entry, so a missing value is reported by `helm` and not by a crash loop.

`api.deliveryTokenSigningKey` and `DELIVERY_TOKEN_SIGNING_KEY` are removed.

### 5. The admin BFF loses its database credentials

Found in the same review: `wholo-admin-api`'s Secret carried `DATABASE_URL`, although `apps/admin-api` never opens a database connection (ADR-026). It is removed. No BFF now holds a secret.

## Consequences

- An anonymous caller can no longer reach the upload parser, or any other delivery-link code, in either service. A caller holding a genuine link still can, which is why the parser itself was patched as well (`multer` 2.4.0).
- A compromised driver BFF cannot mint delivery links.
- Every link printed before the release that introduces this stops working. Acceptable now; from here on, replacing the key no longer has that cost unless it is done as an emergency.
- Deploying this release needs a key pair in `values.live.yaml` first, or the chart will not render (`docs/runbook/deploy.md`).
- There are now two values to keep consistent. The start-up check in `apps/api` and the ordered steps in the runbook exist to catch a mismatch before drivers do.
- `apps/api`'s throttle on these routes still sees every driver as one caller, because requests arrive from the BFF's address. With forged tokens now dropped at the BFF, junk traffic can no longer consume that allowance, but real drivers still share it. Left for a separate change.
- A future public endpoint with its own credential should follow this shape: verify in a guard, before any interceptor, in the BFF and again in `apps/api`, with a public-key check at the edge.
