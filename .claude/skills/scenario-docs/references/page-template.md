# Page template

Written where `scripts/relayout.py --where <id>` says: usually
`<docs_dir>/<audience>/<section path>/<id>.mdx` (config.md, "Audiences and sections").
Sections in this order; leave out any that would be empty. `<scenarios folder>` in the
header comment is that folder's path from the repo root, as the page's readers would
find it (e.g. `documentation/scenarios`).

## Details

**Front matter.** `custom_edit_url: null` hides the "Edit this page" link, which would
otherwise send people to a generated file. If the user would rather it pointed at the
scenario, set it to the scenario's URL in their repo instead.

**Intro.** One job: tell readers what they'll do and end up with, so they can tell at a
glance whether this is the guide they need ("Create a delivery profile: choose the days
you deliver, set the order cut-off, and block any dates you can't deliver."). Keep it
general: the scenario's example values belong in the steps. When there's an About
section, the intro gives no definitions and no reasons, since About covers both. With no
About section, one short clause on why the task matters is fine.

**About.** Only when the scenario has a Concept section. Name the heading after the
concept in the reader's words ("About delivery profiles"), not "Concept". Keep the
scenario's meaning and claims: tidy the wording for the audience, but don't add
behaviour it didn't state. The intro says what the reader is about to do; this section
says what the thing is and why it matters. Don't repeat one in the other: read them
together before saving, and cut any idea that appears in both from the intro.

**Choices and states.** Every option the reader picks and every status they're shown
is explained where they meet it, from the terms file (terms-format.md), in a clause, not
a separate section: "select **Active** (1), so customers can see and order it; **Draft**
and **Archived** both keep it hidden from customers". Name the
alternatives when the reader chooses; for a state, one clause on what it means for them
("**Pending invite**: they can't order until you activate them"). Explain each term
once per page, the first time. Don't explain buttons that say what they do (Save,
Cancel). When a step leaves a choice at its default ("leave **Product type** as
**None**"), say what the default means if the terms file does.

**Before you start.** Only what's true in a reader's world ("A customer called Acme
Bakery exists" → "You'll need at least one customer."). Leave out what exists to make
the run repeatable ("No profile named 'Western Suburbs' exists"). Never mention the
seed, persona ids or demo data.

**Steps.** One `## <n>. <title>` per logical step in the scenario, in order, keeping
"(optional)" if present. Rephrase a title only if it reads badly for the reader. Use
`##` (not `###`) so steps show in Docusaurus's table of contents. The step *body* is
where the route goes: the scenario says "Set its delivery profile to Western Suburbs",
the page says "Under **Delivery**, open the **Delivery profile** list (1) and choose
**Western Suburbs**."

**Instructions.** Second person, imperative, short. Bold on-screen labels and the values
to enter: "In **Name**, enter **Western Suburbs**." Use the labels you saw on screen,
not the scenario's paraphrase, since those are what the reader looks for. Example values
from the scenario are fine to show as examples; keep relative dates relative ("a
Thursday next month").

**Callouts.** `screenshotting-apps` numbers annotations 1, 2, 3 per screenshot. Mention
each one once, in the step that owns the screenshot, in the order drawn. A step without
a screenshot is text only: no callout numbers, and never reuse an earlier image.

**Images.** Relative paths (`./img/<id>/<name>.png`) so they move with the page and
Docusaurus checks they exist. Alt text says what the shot shows, not "screenshot of".

**Admonitions.** `:::note` for behaviour readers wouldn't guess, `:::warning` for
consequences from `Mention:`. Opening and closing `:::` on their own lines, with blank
lines around the content.

**Tone check before saving.** Read it as the audience would. Every sentence should help
them do the task or avoid a mistake; cut anything that's there to sound thorough.
